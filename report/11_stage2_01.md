# 验收报告 · 第11章 · boot/stage2.s

**对照规范:** SPEC/11-boot-stage2.md
**审查文件:** boot/stage2.s（当前 672 行，规范文档描述的是 v1 版本 1003 行）；同时涉及 link.ld、makefile 中与 stage2 构建相关的规则
**结论:** REVISE（发现 1 处会静默降级内存探测功能的 bug，1 处会在特定构建顺序下让 `make` 直接失败的构建系统 bug；均已给出验证证据）

## 架构范围说明（非缺陷，先讲清楚对照口径）

SPEC/11 描述的是 v1 的 stage2：一份文件里同时干三件事——FAT32 找 `DEBUG` 内核直接拷到 1MB、A20/E820/VBE 采集、PM 切换后用内核自带 ABI 表（槽位 49/50/51）跳入口，外加一个 `tramp_int10` 运行时蹦床。当前 v2 的 stage2.s 只保留了"A20/E820/VBE 采集 + FAT 找一个文件并加载 + PM 切换"这部分，且找的不是 `DEBUG` 内核而是 `LOADER.BIN`（stage2.5）；ABI 表机制被搬到了 loader.bin → monitor 这条链路上（`monitor/abi.c`），`tramp_int10` 目前完全没有实现。这是本次会话里逐步定下来的架构改动，不是遗漏，以下审查只针对 stage2.s **现在实际承担的职责**，不对"没有 tramp_int10""没有直接读 ABI 槽 49/50/51"这类因架构重构而不再适用的条目打 X。

## 验证方法

- 通读源码，逐条核对 A20（BIOS 2401h / 键盘控制器 0xd1+0xdf / 快速 A20 端口 0x92）、E820（INT 15h AX=E820h）、E801 回退、VBE（INT 10h AX=4F00h/4F01h/4F15h）几段的寄存器/端口用法与标准调用约定。
- 用 makefile 实际参数重新汇编、链接：`nasm -f elf32 -DPART_LBA=2048 boot/stage2.s -o boot/stage2.o`，再 `ld -m elf_i386 -T link.ld -nostdlib -o bin/stage2.elf boot/stage2.o`，`objcopy --only-section=.stage2.entry` 切出 `stage2.bin`，无警告无错误。
- 用 `ndisasm -b16 -o0x900` 把构建出的 `stage2.bin` 按实模式反汇编，逐条指令核对关键分支（尤其是标志位相关的跳转）与源码语义是否一致。
- 故意把 `link.ld` 的 `STUB_SECTS` 从 8 改成 1 重新链接，确认 `ASSERT(__stub_end <= 0x900 + STUB_SECTS*512, ...)` 真的会在违反时把链接失败（不是摆设注释）。
- 分别用顺序 `make all` 和并行 `make -j4 all` 从全干净状态（`rm -rf bin fsroot lwcnc.img tools/mkfat/mkfat boot/*.o monitor/*.o`）各构建一遍，另外单独跑 `make bin/stage2.bin bin/mbr.bin` 检验构建图对目标顺序是否敏感。

## 检查结果（bug）

### 1. E820 采集存在等值判断误用跳转条件的 bug，导致 E820 分支永远采集不到任何条目

`boot/stage2.s:176-177`：
```asm
    cmp eax, 0x534d4150
    jnc .done
```
反汇编确认这两行确实被汇编成：
```
000009F9  663D50414D53      cmp eax,0x534d4150
000009FF  7324              jnc 0xa25
```
`jnc`（机器码 `0x73`，即 JAE/JNC）判断的是**无符号大小比较**的进位标志，不是"是否相等"。`int 0x15` AX=E820h 调用成功时，EAX 会被 BIOS 原样写回签名 `'SMAP'`（0x534D4150）——也就是说，在**完全正常、BIOS 真的支持 E820** 的情况下，`cmp eax,0x534d4150` 算出的正是 `eax == 立即数`，此时 CF=0，`jnc` **必定跳转**到 `.done`，且这时候 `bp` 还没来得及自增（跳转发生在第一次探测、`inc bp` 之前），于是 `.done` 里 `test bp,bp; jz .fallback` 判定"一个条目都没采到"，无条件退回 E801 回退分支。

也就是说，**只要 BIOS 正确支持 E820，这段代码反而会立刻放弃它**，永远走 E801 那条路——跟"BIOS 不支持 E820 才用 E801 兜底"的设计意图完全相反。对照文件里其它等值判断（比如 VBE 那段 `cmp ax,0x4f; jnz ...`,反汇编为 `83F84F` + `0F850D01`）用的都是正确的 `jnz/jz`，可以确认这里是把 `jne` 误写成了 `jnc`，是局部的书写错误，不是全文件的风格选择。

**修法:** 第 177 行 `jnc .done` 改成 `jne .done`。

### 2. E801 回退路径本身也不完整：只报告 1MB~16MB 之间的内存,16MB 以上全部丢失

`boot/stage2.s:200-231` 的 `.fallback`（E801）分支，只用了 `int 15h AX=E801h` 返回值里的 `cx`（1MB-16MB 之间的 1K 块数），拼出一条 `base=0x100000, len=cx<<10` 的条目，**从未使用 `dx`/`bx`（16MB 以上、按 64KB 计的部分）**，也没有为 16MB 以上的内存追加第三条 ARDS 记录。

由于第 1 条 bug 会让 E820（本该报出完整内存布局）永远走不到,现状是**任何配置了 ≥16MB 内存的机器（现在几乎所有真实/虚拟机器）**,通过这条路径拿到的内存表都会把 16MB 以上的所有内存直接漏报——这不是"某种极端情况才触发"的边角问题,是当前构建下每次启动都会发生的。

两个 bug 叠加的实际后果：**`0x8000` 处的内存表目前永远采不到 E820 的准确数据，也永远漏报 16MB 以上的物理内存**，静默发生，不会有任何错误提示，只会在后续用这张表做内存分配时表现为"能用的内存比机器实际的少一大截"。

### 3. `bin/stage2.elf` 的构建规则缺一个目录依赖，在特定构建顺序下会让 `make` 直接失败

`makefile:79-80`：
```makefile
$(ELF): $(OBJS) link.ld
	$(TOOL_LD) $(LDFLAGS) -o $@ $(OBJS)
```
`$(MBR)`、`$(LOADER_ELF)`、`$(LOADER_BIN)` 这几条兄弟规则都写了 `| $(BIN_DIR)`（order-only，保证 `bin/` 目录先存在），唯独这条 `$(ELF)`（也就是 `bin/stage2.elf`）没写。复现：

```
$ rm -rf bin
$ make bin/stage2.bin bin/mbr.bin
ld -m elf_i386 -T link.ld -nostdlib -o bin/stage2.elf boot/stage2.o
/usr/bin/ld: cannot open output file bin/stage2.elf: No such file or directory
make: *** [makefile:80: bin/stage2.elf] Error 1
```
之所以平时 `make all`（顺序执行）看起来没事，是因为 `$(IMG)` 的依赖列表里 `$(MBR)` 排在 `$(STAGE2)` 前面，`$(MBR)` 自己那条 `| $(BIN_DIR)` 先把目录建出来，`$(ELF)` 才侥幸蹭到一个已存在的目录——这是构建顺序上的运气，不是依赖图本身保证的，换一种目标顺序（就像上面单独指定 `bin/stage2.bin bin/mbr.bin` 这种顺序）就会直接炸。`make -j4 all` 这次测试凑巧也过了，同样是调度顺序凑巧，不代表并行构建下必然安全。

**修法:** 第 79 行补上 `| $(BIN_DIR)`：
```makefile
$(ELF): $(OBJS) link.ld | $(BIN_DIR)
```

## 备注（非缺陷，仅记录）

- **`STUB_SECTS` 预算验证通过。** 实测 `bin/stage2.bin` 为 1494 字节，`STUB_SECTS=8` 对应的预算是 4096 字节，余量 63.5%；人为把 `STUB_SECTS` 改成 1 重新链接会立刻报 `STAGE2 EXCEEDS ITS SECTOR BUDGET`，确认这条 `ASSERT` 是真的在生效，不是摆设。
- **`VIB`/`FAT_SCRATCH` 共用同一物理地址（0x9100）的隐性调用顺序约定仍然成立且被遵守。** `stage2_entry` 里 `call loader_load` 在 `call vbs_harvest` 之前（stage2.s:51/54），FAT 遍历用完 `FAT_SCRATCH` 之后 `vbs_harvest` 才开始往同一地址写 VBE 数据，顺序正确。这仍然是 SPEC 自己点名过的"靠调用顺序而非结构性保证"的隐患，本次没有引入新问题，也没有解决，原样记录。
- **`loader_load` 的文件加载循环没有任何越界保护。** `.file_next_cluster`（stage2.s:528-544）每读一簇就把目标指针 `si` 加 0x20，从不检查是否超出某个上限。SPEC/11 提到 v1 的对应逻辑"拒绝会超出 `KERNEL_COPY_MAX` 的簇链"，v2 这里没有等价检查。当前 `LOADER.BIN` 只有约 2KB，暂时不会触发，但这是一个相对于规范要求缺失的安全网，建议在 loader.bin 体积开始增长前补上一个上限判断。
- **`link.ld` 里的 `STACK_SIZE = 16K;`（第 3 行）是死变量。** 现在的 `link.ld` 只剩 `.stage2.entry` 一个段，没有 `.bss`/栈预留区（stage2 的栈是代码里直接 `mov sp, 0x900` 设的），这个变量没有任何地方引用，是简化 `link.ld` 时的残留，建议删掉。
- **快速 A20（端口 0x92）分支里"若该位已经是 1 就直接判失败"的写法（stage2.s:89-91）值得留意但不算确认的 bug。** 读到 `al` 的 bit1 已经是 1 时直接跳 `.fail`，而不是继续尝试——这在"前面两种方法都没能让 wraparound 测试通过，且这个端口却报告 A20 已经开着"这种矛盾状态下选择报错止损，是可以自洽的保守设计，但没有进一步复核硬件状态就放弃，建议后续留意是否需要更细致的处理。
- **键盘控制器 A20 方法直接写死 `0xdf` 到输出端口（stage2.s:83-84），没有先读回原值做 read-modify-write。** 是很多同类 bootloader 常见的简化写法，对典型硬件没问题，比标准做法略糙，不算错误。

## 判定

发现 2 处功能性问题（E820 恒定失效 + E801 漏报 16MB 以上内存）和 1 处构建系统问题（`bin/stage2.elf` 缺少目录依赖，特定顺序下 `make` 直接失败）。第 3 条修复成本极低（加一个 order-only 依赖）；第 1/2 条需要实际改动 `e820_collecct` 的判断逻辑，并决定是否要把 E801 回退也补上 16MB 以上那部分。本章暂不通过，建议按上述三点改完后再提交复审。
