# Boot: ISR stubs + debug-monitor context switch

**Files:** boot/isr.s (160 lines)
**Status:** compiled and linked normally into the kernel ELF (`boot/isr.o` in `$(OBJS)`, via the generic `boot/%.o` rule — it does not need `PART_LBA` so it isn't special-cased like stage2.o). Lives in `.kernel` at 1MB like any other kernel object, *not* real-mode code, despite sitting in `boot/`.

## Purpose
This is not "boot" code in the sense of mbr.s/stage2.s — it's the exception-vector entry table and a single-step/breakpoint debug-monitor mechanism, physically filed under `boot/` alongside the two real files that get the machine into protected mode. It has two responsibilities:
1. **48 interrupt/exception entry stubs** (`isr0`..`isr47`), generated by a nasm macro/`%rep` pair, that normalize the CPU's inconsistent error-code-pushing behavior (vectors 8, 10-14, 17, 21 push one; everything else doesn't) into one uniform stack layout, then jump to a common handler.
2. **`dbg_enter`/`isr_common`**, a paired mechanism that lets the kernel's monitor (kernel/main.c, not read for this chapter) run arbitrary "debuggee" code and get control back — via any exception, not just a deliberate breakpoint — with the debuggee's full register state captured into a `struct ctx` the C side can inspect and edit before resuming or aborting.

This is the mechanism behind the hand-typed-code workflow the abi-table-contract memory note describes: the user types code into memory and runs it via this monitor, and *any* fault it causes (a wild write, a bad opcode, a page fault if paging existed) lands back in the monitor instead of crashing the machine, because every exception vector ultimately funnels through `isr_common`.

## Public interface
- `isr_table` (line 151): array of 48 `dd` entries, one per vector, consumed by `kernel/idt.c`'s `idt_init()` to populate IDT gate descriptors. This is the only way the C side learns the ISR entry addresses.
- `dbg_enter` (line 108): `void dbg_enter(struct ctx *c)` — C-callable (cdecl). Loads the register/segment/flags state from `*c`, builds an `iret` frame on the debuggee's *own* stack (using `c->esp`, not the monitor's), and `iret`s into it. Returns (to the *caller* of `dbg_enter`, not via a normal `ret` path — see below) only when the debuggee hits any exception; at that point `*c` has been overwritten with the state at the fault.
- `cur_ctx` (line 146) and `in_debuggee` (line 147): extern globals declared in kernel/ctx.h, read/written by both this file and (presumably) kernel/main.c to know which `struct ctx` to fill and whether a debuggee is currently running.
- No ABI slots — this is wired into the IDT, not called through the 0x100000 table.

## Key structures / state
- `struct ctx` layout (mirrored exactly from kernel/ctx.h, whose comment says "hardcoded in boot/isr.s — change one, change both"): eax/ecx/edx/ebx at 0/4/8/12, esp/ebp/esi/edi at 16/20/24/28, eip/eflags at 32/36, cs/ds/es/fs/gs/ss at 40/44/48/52/56/60, vector/errcode at 64/68. 72 bytes total, matching `panic_ctx: resb 72` (line 160).
- `panic_ctx` (line 160, `.bss`): a static fallback `struct ctx` that `cur_ctx` points to *before* any `dbg_enter` call has run — meaning a fault that happens before the monitor ever starts a debuggee still has somewhere valid to land (routed to `dbg_panic`, see below).
- The `isr_common` stack-offset arithmetic (lines 44-87) is a manual map of the `pushad`+segment-push frame it just built (`+0=gs +4=fs +8=es +12=ds, +16..47=pushad, +48=vector +52=errcode +56=eip +60=cs +64=eflags`) — this comment is the only place that layout is written down; it isn't derived from any symbolic offset table.
- `mon_esp` (line 148): saves the monitor's own `esp` across the "monitor calls `dbg_enter`, debuggee faults, `isr_common` needs to get back to the monitor" round trip — the mechanism that makes `dbg_enter` behave like a function call even though the actual return path is via an interrupt, not a `ret` at the call site.

## Dependencies
- `kernel/ctx.h`'s `struct ctx` field order/offsets (hard dependency, unenforced by any static assert on either side — unlike the ABI table and boot-info-block layouts, which do have `_Static_assert` guards on the C side per the abi-table-contract and harvest-block-design notes, there's no equivalent check here tying `ctx.h`'s field order to this file's offset arithmetic).
- `kernel/idt.c`'s `idt_init()` reads `isr_table` to build IDT gates, and sets gate selector `CODE_SEL=0x08` (also hardcoded independently in this file's `isr_common` as `mov ax, 0x10` for `ds`/`es` — 0x10 is the *data* selector, not `CODE_SEL`; these are two different selectors used for two different purposes and happen to both be small constants, worth double-checking they're not accidentally the same magic number reused for different meanings).
- `dbg_panic` (extern, kernel/idt.c) — called when `in_debuggee` is 0 at fault time, i.e. the monitor itself faulted; per that function's own comment, this is unrecoverable and just prints state and halts.
- Downstream: kernel/main.c (not covered by this chapter) is presumably the sole caller of `dbg_enter` and the reader of `cur_ctx`/`struct ctx` after it returns.

## Design notes worth keeping
- The uniform-stack-layout trick (`ISR_ERR`/`ISR_NOERR` macros, lines 11-21) pushing a dummy 0 error code for vectors that don't have one is the standard, correct way to make 48 differently-shaped hardware entry points converge on one handler — nothing unusual here, just worth preserving as-is.
- `isr_common` always switches `ds`/`es` to the monitor's own data segment (line 41-43) *before* touching `cur_ctx` or any other memory, with an explicit comment explaining why: "the debuggee may have changed DS." This is load-bearing — without it, a debuggee that loaded garbage into `ds` would make the very next memory access by the handler itself fault.
- Segment/`iret` restoration is done through `cs` semantics implicitly: at `dbg_enter` (lines 125-132), `ds/es/fs/gs` are loaded from the saved context *before* building the stack frame that `iret` will consume, and the target `esp` for the frame is the *debuggee's* `esp` (`ebx+16`), not the monitor's — meaning the debuggee genuinely runs on its own stack, not borrowed monitor stack, matching how a monitor debugging arbitrary hand-typed code needs to work.
- The two-path exit at the end of `isr_common` (lines 89-105): if `in_debuggee` is set, restore the monitor's saved `esp`/registers and `ret` (back into `dbg_enter`'s caller — the illusion of `dbg_enter` being a normal call); if not, the fault happened in the monitor itself, which is unrecoverable by construction (no saved "outer" state to unwind to) so it goes to `dbg_panic` and halts. This asymmetry is correct and intentional, not an oversight.

## Messiness / review notes
- No static/compile-time check ties `kernel/ctx.h`'s field order to `isr_common`'s hardcoded stack offsets (lines 46-87) or to `dbg_enter`'s offsets (lines 116-141) — unlike the ABI table (`link.ld` ASSERTs) and the boot info block (`_Static_assert` in binfo.c), this cross-language contract is enforced by nothing but the comment on ctx.h line 6. A field reorder in ctx.h that isn't mirrored here would silently corrupt every register value the monitor displays or restores, with no build failure.
- The file is filed under `boot/` even though it has nothing to do with the boot sequence — it's a runtime kernel service (the debug monitor's fault-trampoline) that happens to share a directory with the two genuinely boot-time files. This is a naming/organization inconsistency worth flagging for the rewrite: `boot/` currently means both "runs before the kernel exists" (mbr.s, most of stage2.s) and "kernel-linked low-level CPU-mode-transition code" (isr.s, and arguably `tramp_int10` inside stage2.s per spec/11's own notes) without a directory boundary marking the difference.
- `mov ax, 0x10` (line 41) for the monitor's data selector is a bare magic number with no named constant in this file, while `kernel/idt.c` defines `CODE_SEL 0x08` as a named constant for the *code* selector used to build IDT gates. The data selector value isn't named anywhere in either file — a reader has to infer "0x10 must be the data segment" from context (it follows 0x08 by 8 bytes in a flat GDT) rather than from a label.
- No comment explains *why* vector selection for `ISR_ERR` (line 25: `v == 8 || v == 17 || v == 21 || (v >= 10 && v <= 14)`) matches those specific numbers beyond "the CPU pushes an error code here" (line 10) — correct per the x86 exception reference, but the file doesn't cite that reference or explain the vector *names* (e.g. why 21 specifically — #CP control protection, per kernel/idt.c's `names[]` array, which lives in a different file entirely). A reader has to cross-reference kernel/idt.c to know what vector 21 even is.

## Open questions for the rewrite
- Should this file move out of `boot/` into `kernel/` (or a new `debug/`/`monitor/` directory) to reflect that it's a kernel runtime service, not part of the boot sequence — freeing `boot/` to mean exactly "real-mode-to-protected-mode transition code," matching the observation in spec/11 that `tramp_int10` has a similar mismatch?
- Worth adding a `_Static_assert`-style cross-check (even an indirect one, e.g. the C side computing and comparing a checksum of expected offsets, or simply a shared generated header nasm and gcc both consume) so `ctx.h` and `isr.s` can't silently drift the way link.ld/binfo.c already guard against for the ABI table and boot info block?
- Should the bare `0x10`/`0x08` selector constants get named equivalents shared between kernel/idt.c and boot/isr.s (a generated header, or just duplicated named `equ`/`#define` pairs with a comment pointing at each other, matching the existing convention used for the ABI slot numbers and boot-info offsets)?
- Is the vector-name table (`kernel/idt.c`'s `names[]`) worth pulling next to the `ISR_ERR`/`ISR_NOERR` classification in this file, or kept separate since one is asm-generation-time and the other is runtime-display?
