# Boot: Stage2 (real-mode stub + PM entry + BIOS trampoline)

**Files:** boot/stage2.s (1003 lines)
**Status:** compiled as part of the single ELF link (`boot/stage2.o` in `$(OBJS)`), but split back out of that ELF into *two* independent pieces by `objcopy`: `--only-section=.stage2.entry` becomes `stage2.bin` (real-mode-only code, written to sector 1 of the image by the MBR's load), and the file's 32-bit `pm_entry`/`tramp_int10` code lives in `.stage2.entry` too (see link.ld — the whole file is one section, not split by bitness) so it travels with the stub, not with `.kernel`. The stub is never loaded from a fixed kernel-image offset; the *kernel proper* (`kernel/*.o` objects) is instead written into the FAT32 partition as a file named `debug` and found by this file's own FAT walk at boot.

## Purpose
Three jobs, run in sequence from `stage2_entry`, entirely in real mode, before anything is "the kernel":
1. **Find and load the kernel.** Walk a FAT32 filesystem (whose location on disk this file doesn't know at build time — it only knows `PART_LBA`) to find a file named `DEBUG` and stream its cluster chain to `KERNEL_LOAD_PHYS` (0x10000). This replaced an earlier design where the kernel rode along in the MBR's own read at a fixed sector.
2. **Collect what real mode can see that protected mode can't**: enable A20, walk the BIOS E820/E801 memory map into 0x8000, and harvest VBE controller/mode/EDID info into the boot info block at 0x9000 (see spec/xx-kernel-binfo.md for the reader side).
3. **Switch to protected mode**, copy the loaded kernel up to 1MB, zero its BSS, and call its entry point — using addresses read out of the *loaded kernel's own* ABI table rather than anything baked into this build, because the kernel that ends up on disk in `fsroot/` can be rebuilt independently of this stub.

A fourth, logically separate piece of code lives in the same file: `tramp_int10`, a protected-mode-callable routine that drops back to real mode, runs one `int 10h`, and returns to protected mode — callable *after* boot, from the running kernel, via ABI slots 45-48 (see the bios-trampoline design note). It shares this file only because it's real-mode code that must live below 1MB, same constraint as the stub.

## Public interface
- `stage2_entry` (line 113): entered by the MBR at 0000:0900, real mode, `dl` = boot drive. Never returns.
- `tramp_int10` (line 840): `void tramp_int10(void)`, cdecl, no arguments — reads `TRAMP_REGS` at 0xA018, writes results back into the same block. Reachable directly by address from 32-bit kernel code post-boot because everything is flat/identity-mapped and no paging exists. Exposed to hand-typed code via ABI slot `tramp_call` (see kernel/abi.h and the bios-trampoline memory note); slots `gfx_enter`/`gfx_exit`/`gfx_live` are kernel-side wrappers, not in this file.
- No other label in this file is called from outside it.

## Key structures / state
Everything below 1MB is addressed by fixed absolute constant, not as section-relative labels — the file comment at lines 52-55 explains why: as section labels in `.stage2.entry` they'd be forward references nasm can't size, causing a "label changed during code generation" convergence failure. So every one of these is a build-time constant, not a linker symbol:
- **0x8000-0x8a10**: E820/E801 ARDS table (`MMAP_BASE` etc, lines 18-23), format: 4-byte magic 'ARDS', 4-byte count, 4-byte flags, then up to 128×20-byte entries.
- **0x8A10-0x8A1C**: `FAT_START_LBA`/`DATA_START_LBA`/`cur_cluster` (lines 757-759) — kernel_load's own persistent scratch, placed in the gap between the E820 table and the boot info block.
- **0x9000-0x90E4**: boot info block (`BINFO_BASE`, lines 27-47) — mirrors `kernel/binfo.h`'s C struct field-for-field; the file comment says the C side's `_Static_assert`s fail the build if they drift.
- **0x90EE/0x90F0**: `BOOT_DRIVE`/`KDAP` (lines 69-70) — deliberately in the 0x90E4..0x9100 gap so `vbe_harvest`'s block-zeroing doesn't clobber them.
- **0x9100-0xA000**: VBE scratch (`VIB`, `MIB`, `MODELIST`, VBE ROM's borrowed stack top) — reused as `FAT_SCRATCH` (line 86) by `kernel_load`, which the comment there notes is provably safe since nothing touches VIB until `vbe_harvest` runs afterward.
- **0xA000-0xC000**: `TRAMP_BLK` (lines 92-111) — `tramp_int10`'s save area (esp, PIC masks, GDTR/IDTR, register block) plus its own 7.9KB ROM stack, mirrored by `tramp_regs_t` in kernel/tramp.h.
- **0x10000**: `KERNEL_LOAD_PHYS` — where the FAT-walked kernel file lands before the PM copy to 1MB. `KERNEL_COPY_MAX` (0x90000, 576KB) is always copied in full regardless of actual kernel size (line 74-80 comment: harmless, unclaimed RAM until BSS zeroing).
- **1MB (`0x100000`)**: after the copy, `ABI_BSS_START`/`ABI_STACK_TOP`/`ABI_KMAIN_ENTRY` (lines 766-768) are read from the *copied* kernel's own ABI table (slots 49/50/51, duplicated from kernel/abi.h since nasm can't `#include` a C header) — not from this build's own linker symbols. This is the mechanism that decouples the stub's build from the kernel's build.
- `gdt_start`/`gdt_code`/`gdt_data`/`gdt_code16`/`gdt_data16` (lines 974-987): the one GDT used both for the initial PM switch and every `tramp_int10` round trip. Kept in `.stage2.entry` (not `.rodata`, which lives at 1MB) because `lgdt` runs in real mode and can't reach a 1MB operand (per the boot-memory-layout note).

## Dependencies
- `PART_LBA` from the makefile (`-D`), must agree with boot/mbr.s and tools/mkfat.py.
- `KERNEL_LOAD_PHYS`/`KERNEL_COPY_MAX` mirror link.ld's `KERNEL_LOAD_PHYS` and the 0xA0000 VGA-hole ceiling; link.ld's ASSERT enforces the *kernel's* build-time size against that ceiling, this file enforces nothing itself (it always copies the max) but its FAT walk (`kernel_load`, line 642-643) does reject a cluster chain that would overrun `KERNEL_COPY_MAX`.
- `kernel/abi.h`'s slot numbers 49/50/51 (`LW_SLOT_BSS_START`/`STACK_TOP`/`KMAIN_ENTRY`) and the magic `0x4241574C` ('LWAB') — hand-duplicated here as `LW_ABI_MAGIC`/`ABI_BSS_START` etc (lines 765-768). See spec/xx-kernel-abi.md; this is the load-bearing cross-language coupling the abi-table-contract memory note describes.
- `kernel/binfo.h`'s struct layout, hand-duplicated as the `BI_*`/`BINFO_*` equ block (lines 27-47).
- `kernel/tramp.h`'s `tramp_regs_t`, hand-duplicated as the `TB_*` equ block (lines 93-106).
- Downstream: everything in kernel/*.c that reads the boot info block, the E820 table, or calls `tramp_int10` depends on this file having filled those structures correctly and consistently with the mirrored C definitions.

## Design notes worth keeping
- The IF/triple-fault story at lines 772-780 is a real, hardware-confirmed bug fix, not speculative caution: a stray PIT tick landing mid-`rep movsb` (during the 576KB kernel copy) with no protected-mode IDT installed yet caused a reliable Bochs triple-fault loop. The `cli` at `pm_entry`'s top is explicitly *not* redundant with `stage2_entry`'s own `cli` — a real-mode BIOS call in between (`vbe_harvest`) isn't guaranteed to preserve IF. Reproduced specifically on Bochs's slower instruction-stepped timing, not QEMU — worth keeping as a note for whoever tests boot changes next (see the kbd-decoder-testing memory on why QEMU is the primary boot-test tool here).
- `kernel_load`'s ABI magic check (line 808) before trusting `ABI_BSS_START` et al: "the loaded kernel might not be the one this stub was linked against" — an explicit skew-tolerance design, not an oversight, since fsroot's `debug` file is rewritable independently of a stage2 rebuild.
- `vbe_harvest` deliberately never calls VBE mode-set (4F02) — the comment at lines 317-321 explains the console still owns 0xB8000 text mode at this point, so setting a graphics mode here would blank the only output channel available. `BINFO_F_MODESET` is left clear specifically to communicate "candidate mode, not active" to readers.
- `tramp_int10`'s four "things that bite" (PIC masking, 16-bit descriptor load order, esp relocation, A20 re-test) are exactly the four the bios-trampoline memory note calls out — the code and the memory agree, and the comments at lines 847-857, 863-875, 859, 930-936 are the primary source for that memory, not a paraphrase of it.
- `read_sector`'s retry-with-controller-reset (lines 707-730): "one spurious failure is normal on real media" — a real-hardware-informed design choice, not defensive boilerplate.

## Messiness / review notes
- This file does three structurally distinct jobs — FAT32 kernel loader, real-mode hardware harvest (A20/E820/VBE), and a general-purpose PM↔RM trampoline — glued together only by the "must live below 1MB" constraint. There's no section boundary or naming convention inside the file marking these apart beyond comment banners (`; ---- ... ----`); a reader has to already know the architecture to know where "boot" ends and "runtime-callable trampoline" begins. `tramp_int10` in particular has nothing to do with booting per se — it's a runtime kernel service that happens to require real-mode code, and its presence here is purely an artifact of the 1MB addressing constraint, not a boot-sequence dependency. This is the single strongest candidate in the whole boot chain for being pulled into its own conceptually-separate unit even though it must stay physically co-located below 1MB.
- Absolute-address addressing (VBE_SP, TRAMP_BLK, etc., all `equ` to hard numbers) throughout is explained once (lines 52-55) but the technique itself — no relocation, no assertions that these regions don't overlap each other — means the "map" of what lives where between 0x500 and 0xC000 exists only in scattered comments across boot-memory-layout.md, harvest-block-design.md, and this file's own header block. There is no single source-of-truth table (in code or docs) enumerating every claimed low-memory region and its bounds; overlap between, say, `TRAMP_BLK` (0xA000) and `VBE_STACK_TOP` (0xA000, *touching* the same address, justified only by a one-line comment on line 90 that ROM stack growth stops exactly at 0xA000) is asserted only in prose, never checked at build or link time the way link.ld checks the stub-size and kernel-size constraints.
- `get_next_cluster` and `kernel_load`'s directory scan reuse `KDAP`/`FAT_SCRATCH` for two different purposes in the same call chain (line 624-628 comment explicitly warns about this), meaning the routine's correctness depends on call-order discipline that isn't enforced by the code shape — a mistake here would be a silent wrong-cluster read, not a crash.
- The file mixes genuinely load-bearing safety code (A20 test-before-enable, retry logic) with debug/harvest code (VBE scoring heuristics) at the same indentation and comment density, making it hard to tell at a glance which failures are "boot cannot continue" (A20, kernel not found) versus "cosmetic, degrade gracefully" (no VBE, no EDID) without reading each `.fail`/`.done`/`.wipe` path individually.
- No test/assertion anywhere in this file (or link.ld) checks that `TRAMP_BLK`'s region (0xA000-0xC000) doesn't collide with anything the VBE harvest or FAT walk still needs live at the moment `tramp_int10` might run post-boot — currently safe only because harvest/FAT-walk are boot-only and `tramp_int10` is post-boot, but that's a temporal invariant, not a structural one.

## Open questions for the rewrite
- Should the trampoline (`tramp_int10` + its GDT/IDT/stack machinery, roughly lines 830-1003) be physically separated from the boot-only code (roughly lines 1-829) into two files that both get assembled into `.stage2.entry`, purely for readability, even though they must still link into the same low-memory section?
- Is it worth building a single generated/checked table of "who owns which low-memory byte range" (0x500-0xC000) rather than relying on scattered prose across four files (this one, boot-memory-layout.md, harvest-block-design.md, bios-trampoline.md)? Could even become a build-time check akin to link.ld's ASSERTs.
- The `KDAP`/`FAT_SCRATCH` dual-use hazard in `kernel_load`/`get_next_cluster` — worth restructuring to use two separate scratch buffers now that there's headroom (the 576KB budget replaced the old ~300-byte one), trading a few hundred bytes of low memory for removing a call-order invariant?
- Does the "kernel not embedded at a fixed offset, found via FAT32 walk instead" design still earn its complexity, now that the 57-sector ceiling that originally motivated it is gone (per boot-memory-layout.md, the ceiling died once the stub got its own `int 13h` read)? Or does the flexibility (rebuilding fsroot's `debug` file independently) still justify it?
- Any interest in a build-time or boot-time self-check that `BINFO_SIZE`/`TB_*` offsets actually match the C headers, beyond the existing `_Static_assert`s on the C side alone — e.g. a magic/version byte the C side also checks against a constant this file defines?
